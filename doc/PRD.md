## 一、问题陈述

### 1.1 背景

用户团队采购了方舟的 Code Plan，但只有 AK（API Key），存在以下核心问题：

1. **无法追踪个人使用情况**：管理员不知道每个团队成员的 AK 使用频率和用量
2. **无法进行有效配额管理**：容易出现个别人过度使用导致团队配额快速耗尽
3. **缺乏成本透明度**：无法准确核算各部门/项目的 AI 使用成本

### 1.2 用户痛点分析

根据瑞思的用户旅程地图和痛点优先级矩阵分析，识别出 **16 个痛点时刻**，其中 **3 个 P0 级痛点** 必须优先解决：

| 痛点编号 | 痛点描述 | 影响人数 | 严重程度 | 频率 | 总分 | 优先级 |
|---------|---------|---------|---------|------|------|---------|
| P4 | 审批流程不透明，不知道进度 | 5 | 4 | 4 | **80** | 🔴 P0 |
| P9 | 不知道 AK 的用量和配额 | 5 | 4 | 4 | **80** | 🔴 P0 |
| P10 | 智能体响应慢或失败，不知道原因 | 4 | 4 | 4 | **64** | 🔴 P0 |

## 二、目标和非目标

### 2.1 目标（Goals）

1. **透明化 AK 使用**：让每个用户和管理员都能实时查看 AK 的用量、配额、费用
2. **精细化配额管理**：支持个人/团队/部门多级配额设置，防止过度使用
3. **智能预警系统**：在配额达到 70%/90%/100% 时自动预警，避免服务中断
4. **多协议兼容支持**：兼容 Anthropic Messages API（`/v1/messages`）和 OpenAI Chat Completions API（`/v1/chat/completions`）协议，支持 Claude、GPT、DeepSeek、Kimi、MiniMax、GLM 等多种模型

### 2.2 非目标（Non-goals）

1. **不做通用 API 网关**：不试图替代 Kong、AWS API Gateway 等通用网关产品
2. **不做复杂权限管理**：不实现细粒度的 RBAC 权限系统（后续版本可考虑）
3. **不做模型训练/微调**：不涉及 AI 模型的训练、微调、部署功能
4. **不做多租户 SaaS**：不面向外部客户提供服务，仅服务内部团队

## 三、用户故事

### 用户故事 1：查看审批进度

**As a** 研发工程师  
**I want to** 实时查看 AK 审批进度  
**So that** 合理安排工作计划，避免焦虑等待

**Acceptance Criteria**:
- Given 用户已提交 AK 申请
- When 用户登录系统查看"我的申请"
- Then 显示当前审批节点、审批人、预计完成时间

### 用户故事 2：实时监控用量和配额

**As a** 智能体用户  
**I want to** 实时查看 AK 的用量和配额  
**So that** 避免服务中断，合理规划使用

**Acceptance Criteria**:
- Given 用户已获取 AK
- When 用户打开"个人监控看板"
- Then 显示当日/本月请求次数、Token 消耗、费用、配额使用率

### 4.3 用量监控模块

#### 核心指标定义（4 大类 30+ 指标）

**个人用量指标**：

| 指标名称 | 字段名 | 说明 | 单位 |
|---------|---------|------|------|
| 日请求次数 | daily_requests | 用户每日 API 请求总数 | 次 |
| 月请求次数 | monthly_requests | 用户每月 API 请求总数 | 次 |
| 请求成功率 | request_success_rate | 成功请求数 / 总请求数 | % |
| 输入 Token 数 | input_tokens | 每日/月输入的 Token 总量 | 个 |
| 输出 Token 数 | output_tokens | 每日/月输出的 Token 总量 | 个 |
| 总 Token 消耗 | total_tokens | input_tokens + output_tokens | 个 |
| 日费用 | daily_cost | 用户每日产生的费用 | 元 |
| 月费用 | monthly_cost | 用户每月产生的费用 | 元 |

#### 监控维度设计（4 个维度）

1. **时间维度**：实时监控（1秒精度）→ 日报（1分钟精度）→ 周报 → 月报
2. **人员维度**：个人 → 团队 → 部门 → 项目
3. **模型维度**：GPT 系列、Claude 系列、文心一言、通义千问、其他模型
4. **功能维度**：代码补全、对话功能、代码解释、单元测试生成、其他功能
5. **厂商维度**：Anthropic、OpenAI、DeepSeek、Kimi、MiniMax、GLM、其他厂商

### 4.4 流量预警模块

#### 预警阈值设置

| 阈值类型 | 提醒阈值 | 警告阈值 | 禁止阈值 |
|---------|---------|---------|---------|
| 个人配额 | 70% | 90% | 100% |
| 团队配额 | 70% | 90% | 100% |
| 个人费用 | 日均费用 2 倍 | 日均费用 5 倍 | - |
| 团队费用 | 预算 5% | 预算 10% | 预算 20% |

#### 预警级别设计（4 个级别）

| 级别 | 触发条件 | 通知方式 | 处理逻辑 |
|------|---------|---------|---------|
| Level 1: 提醒 (Info) | 用量达到配额的 70% | 站内信、邮件 | 记录日志，发送通知 |
| Level 2: 警告 (Warning) | 用量达到配额的 90% | 站内信、邮件、企业微信 | 建议用户/管理员采取行动 |
| Level 3: 严重 (Critical) | 用量达到配额的 100% | 站内信、邮件、企业微信、短信 | 暂停服务，需要人工介入 |
| Level 4: 紧急 (Emergency) | 系统故障、安全漏洞 | 所有可用方式 | 紧急响应，立即采取措施 |

### 4.5 多协议适配层

#### 功能描述

实现多厂商 AI API 协议的适配和转换，支持通过统一接口访问不同厂商的 AI 模型：

1. **Anthropic Messages API 兼容**：支持 `/v1/messages` 接口协议（Claude API 格式）
2. **OpenAI Chat Completions API 兼容**：支持 `/v1/chat/completions` 接口协议（GPT API 格式）
3. **扩展协议支持**：支持 DeepSeek、Kimi（Moonshot）、MiniMax、GLM（智谱 AI）等厂商 API

#### 协议转换流程

**请求流程**：
```
[客户端] → [协议识别] → [格式验证] → [协议转换] → [路由到厂商 API] → [转发请求]
```

**响应流程**：
```
[厂商 API] → [响应接收] → [协议转换] → [格式封装] → [返回客户端]
```

#### 支持的厂商和模型（Phase 1 目标）

| 厂商 | 协议类型 | 支持模型 | 优先级 |
|------|---------|---------|--------|
| Anthropic | Messages API (`/v1/messages`) | Claude 3 系列 | P0 |
| OpenAI | Chat Completions API (`/v1/chat/completions`) | GPT-4 系列、GPT-3.5 系列 | P0 |
| DeepSeek | Chat Completions API (兼容) | DeepSeek-V2、DeepSeek-Coder | P1 |
| Kimi (Moonshot) | Chat Completions API (兼容) | Moonshot-v1 | P1 |
| MiniMax | 自定义 API | abab-v6 | P2 |
| GLM (智谱 AI) | Chat Completions API (兼容) | GLM-4、GLM-3 | P2 |

### 5.2 API 接口设计

#### 个人看板 API

```
GET  /api/v1/dashboard/personal/summary
# 返回：今日请求次数、Token 消耗、费用、配额使用率等

GET  /api/v1/dashboard/personal/trend?period=7d
# 返回：最近 7 天的用量趋势（按小时/天）

GET  /api/v1/dashboard/personal/feature-distribution
# 返回：功能使用分布（饼图数据）

GET  /api/v1/dashboard/personal/model-distribution
# 返回：模型使用分布（饼图数据）
```

#### AK 代理 API（支持多协议）

```
# 多协议代理端点（自动检测协议类型）
ALL /v1/* 
# 功能：自动检测请求协议（/v1/messages → Anthropic, /v1/chat/completions → OpenAI）
# 路由到对应的 provider adapter，转发请求并记录用量
# 请求头：Authorization: Bearer {ak}
# 返回：对应协议的响应 + 用量信息
```

### 5.3 性能影响

#### 性能优化建议

1. **数据缓存**：Redis 缓存热门数据（TTL 30s - 5min）
   - 个人看板汇总数据：缓存 1 分钟
   - 团队看板汇总数据：缓存 30 秒
   - 系统实时指标：缓存 5 秒

2. **数据预聚合**：使用汇总表（daily/weekly/monthly summary）
   - 避免每次查询都扫描原始日志表

3. **分区策略**：对 `usage_logs` 表按月份分区
   ```sql
   ALTER TABLE usage_logs 
   PARTITION BY RANGE (YEAR(timestamp) * 100 + MONTH(timestamp)) (
       PARTITION p202401 VALUES LESS THAN (202402),
       PARTITION p202402 VALUES LESS THAN (202403),
       ...
   );
   ```

## 九、开放问题

1. **方舟 API 的集成方式**：
   - 方舟是否提供标准的 API 接口？
   - 是否支持 AK/SK 的编程式创建和管理？

2. **部署方式**：
   - 是部署在团队内网（私有化部署），还是部署在公有云（SaaS 服务）？
   - 如果是私有化部署，是否需要支持离线环境？

3. **身份认证方式**：
   - 是否对接企业的统一身份认证（如 LDAP、SAML、OAuth2）？
   - 还是使用独立的用户账号体系？

4. **数据合规和隐私**：
   - 用量数据是否需要匿名化处理后才能用于数据分析？
   - 是否需要支持数据本地化存储（如仅存储在国内数据中心）？

5. **多协议差异处理**（新增 v1.1）：
   - 各厂商 API 的请求/响应格式差异如何处理（如 Anthropic vs OpenAI 的 streaming 格式）？
   - 厂商特定参数（如 DeepSeek 的 `top_k`、Kimi 的 `temperature` 范围）如何统一？
